# Project Ceres — Resolved Decisions Archive

Decisions that were open questions and have since been resolved. Moved here from `planning.md`
to keep the active file lean. Decisions that produced ADRs are cross-referenced.

---

- [x] **Authentication?** — Not needed for Phase 1/2 (local). Required in Phase 3 before hosting.
- [x] **Should accounts be linked to a currency?** — Yes. Each account has one currency. Supported at launch: EUR, USD, GBP, COP, ARS, VED. Reports filter by currency — no conversion. See models.md.
- [x] **How to handle transfers between accounts?** — Dedicated Transfer entity linking source and destination directly. No category. Excluded from all income/expense reports. Cross-currency transfers not supported. Has its own Transfer History report. See models.md.
- [x] **Number formatting and localization** — User-configurable preferences in a Settings table. Options: number format (US vs European), date format (DD/MM/YYYY, MM/DD/YYYY, YYYY-MM-DD), date separator. Phase 1: single-row app-wide settings. Phase 3: migrates to per-user preferences. See models.md.
- [x] **Starter categories** — App seeds a default set on first run (6 income, 17 expense categories). Users can add, rename, or delete any of them. Full list in planning.md Phase 1 features section.
- [x] **File attachment storage for Phase 1/2** — Local filesystem using `uploads/{transactionId}/{guid}{extension}`. Files served via controller action, not wwwroot. See models.md for StoredPath convention.
- [x] **Pagination strategy for Transaction History** — See ADR-0027. Phase 1: default view shows the most recent 50 transactions; advanced search / date range filter returns all records in the range with no cap. Phase 3: switch to offset-based pagination (`?page=1&pageSize=50`). Cursor-based deferred unless Phase 3 scale warrants it.
- [x] **Default currency when creating a new account** — Stored as `DefaultCurrencyId` in Settings (FK → Currency). Seeds to EUR on first run. Editable via Settings page. Account creation form pre-selects this currency but allows per-account override. See ADR-0015.
- [x] **Intra-day transaction ordering** — `CreatedAt datetime NOT NULL` added to both Transaction and Transfer. Set by the application on insert, never editable. Used as a tiebreaker when ordering records sharing the same Date. Default sort: `ORDER BY Date DESC, CreatedAt DESC`. See ADR-0013.
- [x] **Budget/transaction currency mismatch** — Enforced at the application level. App validates `transaction.Account.CurrencyId == budget.CurrencyId` and rejects mismatches with a validation error. No database constraint (EF Core cannot express cross-table currency match without a trigger). Integration tests must cover this aggressively. See ADR-0016.
- [x] **Category needs/wants tag for budgeting frameworks** — `LifestyleTag` varchar column added to Category (values: "Needs", "Wants", null = untagged). Seeded categories ship with suggested default tags. Users prompted at Expense category creation time. Untagged is a visible fourth bucket in the Financial Health report. See Financial Health Metrics in planning-phase2.md.
- [x] **Database backup strategy (Phase 1)** — weekly `pg_dump` via macOS `launchd` every Sunday at 7am, output to iCloud Drive (`Database backup/project_ceres_YYYY-MM-DD.sql`). Syncs off-device automatically via iCloud. Before Phase 3 launch, a managed cloud backup solution must replace this local approach.
- [x] **Opening balance cutover UX** — (1) Default starting date is today. User can change it, but the app shows an explanation of how moving the date affects their account balance and history before confirming. (2) Transactions dated before the opening balance date are blocked — not just warned. The app tells the user what they need to do to allow it (move the opening balance date first).
- [x] **Per-account balance audit trail** — Implemented as a dedicated sub-page at `/Accounts/{id}/Ledger`. Shows every entry that contributes to the account balance in chronological order with a running balance column: opening balance (IsSystem transaction), regular transactions, transfers, and liability payments. The final row's running balance must match the balance shown everywhere else in the app. This is the mechanism for validating data model correctness during Phase 1 daily use.
- [x] **React build toolchain** — Vite. Fastest dev server (native ESM), integrates with .NET via `Vite.AspNetCore` NuGet package. See ADR-0032.
- [x] **Frontend test strategy** — Vitest + React Testing Library. Vitest shares the Vite config file and transform pipeline; React Testing Library handles component-level tests. See ADR-0032.
- [x] **Charting library** — Chart.js via `react-chartjs-2` wrapper, confirmed for Phase 2. Covers all seven dashboard chart types. If Phase 3 introduces interactions Chart.js cannot handle cleanly, Recharts is the documented fallback. See ADR-0033.
- [x] **React component file location** — `ProjectCeres.Client/` at the repo root. Follows the Microsoft `ClientApp/` convention (Vite-based), keeps the JS build system isolated from the .NET project, and aligns with the existing `ProjectCeres/` / `ProjectCeres.Tests/` naming pattern. Backend stays as `ProjectCeres/` — no rename.
- [x] **JSON endpoints for React components** — Dedicated `[ApiController]`-attributed controllers in `Controllers/Api/`. Single responsibility enforced: Razor controllers serve HTML, API controllers serve JSON. `InvalidModelStateResponseFactory` overridden in `Program.cs` to match the error shape in `api-contract.md`. See ADR-0035.
- [x] **Factory pattern for report selection** — `ReportGeneratorFactory` introduced at the start of Phase 2, before the first new report generator is written. Each report type is a class implementing `IReportGenerator`. Satisfies OCP (new report = new class, nothing modified) and DIP (controllers depend on the interface). See ADR-0036.
- [x] **Controller action testing strategy** — API controllers tested via `WebApplicationFactory<Program>`. Razor controllers untested (thin, temporary, deleted in Phase 3). CSV import tested at the `ImportService` unit level, not the controller level. See ADR-0037.
- [x] **ImportService test approach** — Option C: unit tests for parsing/sign-flipping/error accumulation; integration tests for full import path. CSV only with helpful XLSX rejection message. Fixture files in `ProjectCeres.Tests/Fixtures/`. See ADR-0038.
- [x] **Cleared/reconciliation status** — `IsCleared bool` on `Transaction` and `Transfer`. Merge-not-delete reconciliation: manually entered transaction survives with all FKs intact, marked cleared; imported row discarded on match. "Different transactions" auto-clears the imported row — no manual follow-up. Fingerprint: date + amount + description + account, ±1 day tolerance. See ADR-0039.
- [x] **One transaction per budget goal** — Single FK (`Transaction.BudgetId`) kept. One transaction → at most one goal budget. Junction table rejected as disproportionate complexity. Documented constraint; migrate in Phase 3 if daily use proves painful. See ADR-0040.
- [x] **Goal budget types** — Two archetypes: `Spending` (tracks tagged expense transactions) and `Savings` (derives progress from a `LinkedAccountId` account balance). `GoalType` enum and `LinkedAccountId` nullable FK added to `Budget`. Phase 2 scope: progress, projected completion, runway indicator, history, honest overspend. Milestones with progress bar UI deferred to Phase 3. See ADR-0040.
- [x] **Split transactions** — Not included in Phase 2. Revisit at Phase 3 scope definition — outcome may be implement, defer again, or discard. 1:1 `Transaction→Category` model kept. Workaround: multiple transactions. See ADR-0041.
- [x] **`TransferAttachment` entity** — In scope for Phase 2. Mirrors `TransactionAttachment` — same schema, same hard delete with confirmation. No reconciliation flow (transfers are internal, not bank-originated). Transfer reconciliation deferred; revisit if needed. See ADR-0042.
- [x] **Interest rate on liability accounts** — In scope for Phase 2. `LiabilityRepaymentType` enum (`FullMonthly` | `Amortising`) and nullable `InterestRate` decimal added to `Account`. UI adapts per type: `FullMonthly` shows no projection; `Amortising` shows payoff projection panel. See ADR-0043.
- [x] **Recurring reminders — notification delivery** — In-app only for Phase 2 (dashboard banner, reminders view, nav badge). No background process. Email push deferred to Phase 3 alongside the email service. See ADR-0044.
- [x] **Recurring reminders — `DayOfPeriod` behaviour** — Both behaviours coexist via `ReminderBehaviour` enum (`SnapToCalendarDay` default | `RelativeToLastConfirmation`). Snap always lands on `DayOfPeriod`, forwarding if confirmed late. Relative = confirmation date + period. See ADR-0045.
- [x] **OFX import** — Deferred. Not included in Phase 2. Revisit at Phase 3 or Phase 4 based on real usage data — implement, defer again, or discard. See ADR-0046.
- [x] **CSV column mapping UX** — Manual mapping UI on first import, saved as named `CsvImportProfile` with JSON field mappings. Auto-applied on subsequent imports. Edit in place (diff confirmation), create new, rename supported. Soft delete with `DeletedAt`, 90-day visible recovery window, no silent auto-purge. See ADR-0047.
- [x] **Irregular income baseline budgeting** — Deferred to Phase 3. Fixed budget model validated first in Phase 2 daily use. Rolling average baseline is the natural next layer on top of existing `LifestyleTag` groundwork. See ADR-0048.
- [x] **"Can I afford this right now?" financial health snapshot** — Included in Phase 2. Always-on dashboard panel: runway = (assets − liabilities) ÷ avg monthly expenses; income vs 6-month rolling average; budget burn rate. No new schema — `DashboardService` extended. See ADR-0049.
- [x] **Tax reserve envelopes** — Dedicated reserve account via transfers. `ExcludeFromSpendable bool` on `Account`. Spendable balance excludes flagged accounts; net worth unaffected. See ADR-0050.
- [x] **Upcoming payments view** — Read-only view from recurring transaction templates due in 30 days. Named "Upcoming Payments". `ReminderBehaviour` extended with `ManualDate` — user sets next due date manually on confirmation. No new entity. See ADR-0051.
- [x] **Liability payoff projection UI** — In Phase 2. Projection panel on `Amortising` account view: payoff date, total interest, "what if €X extra" scenario. See ADR-0052.
- [x] **Guided onboarding** — Deferred to Phase 3. Build alongside multi-tenancy as the first impression for beta users. See ADR-0053.
- [x] **Nice-to-have reports — priority order** — Confirmed Phase 2: Budget vs. Actual, Largest Expenses, Monthly Cash Flow Trend, Net Worth Over Time. Deferred to Phase 3: Spending by Category Over Time, Year-over-Year Comparison. See ADR-0054.
- [x] **InvestmentHolding entity** — Deferred to Phase 3 or Phase 4. Revisit based on whether investment accounts are actively used in Phase 2 daily use.
- [x] **Saved report configurations** — Deferred to Phase 3. Insufficient usage experience in Phase 2 to know what parameters are worth saving or what a report builder should look like. Reassess after Phase 2 daily use. See ADR-0055.
- [x] **`GetActualSpendAsync` date scope** — Caller always specifies `year` and `month`. No default overload. Dashboard passes `DateTime.Today.Year` / `DateTime.Today.Month`; Budget vs. Actual report (Stage 7) passes historical months. Prevents a signature-breaking refactor at Stage 7. See ADR-0056.
- [x] **`BudgetsController` single vs. split** — Single `BudgetsController` for Phase 2, covering both `CategoryBudget` and goal budget CRUD (~12 actions). All logic stays in the service layer so a future split is a routing-only change. Split trigger documented in ADR-0057. See ADR-0057.
- [x] **Authentication framework for Phase 3** — ASP.NET Core Identity with email/password + Argon2id hashing (m=19456, t=2, p=1). **TOTP MFA: opt-in** per [ADR-0069](decisions/ADR-0069-mfa-opt-in-for-personal-users.md) — originally mandated; reversed on 2026-05-09 (industry-norm survey + onboarding-conversion data + NIST SP 800-63B-4 AAL1 classification all argue for opt-in; compensating-control stack closes the credential-stuffing gap for non-MFA accounts). Social login deferred to Phase 4 per ADR-0064 — Phase 3 ships email + password + (opt-in) TOTP only, with the architecture (cookie `SameSite=Lax`, provider-agnostic `UserSession`) kept open for later. API auth: cookie-based (HttpOnly session cookie) in Phase 3; JWT deferred to Phase 4 for mobile clients. See `planning-phase3.md → Authentication`, `api-contract.md → Authentication`, ADR-0063 (cookie SameSite), ADR-0064 (social login deferral), and ADR-0069 (MFA opt-in).
- [x] **Multi-tenancy implementation** — `UserId uuid NOT NULL FK → AspNetUsers.Id` added to every user-owned entity. HMAC pseudonymisation: every data row stores `UserRef = HMAC-SHA256(USER_REF_SECRET, userId)` so a DB dump cannot link records to real identities without the server secret. Full entity list and migration plan documented in `docs/multi-tenancy-strategy.md`.
- [x] **Settings migration for Phase 3** — Single-row Phase 1 Settings table becomes per-user. Migration: the existing Settings row is **remapped to the first registered user** along with the rest of the sentinel-tagged rows per ADR-0066, preserving the developer's existing preferences. Subsequent users get a default Settings row created on registration, seeded with system defaults (`Language = 'en'`, `Country = null`, `NumberFormat = 'comma_decimal'`, `DateFormat = 'DD/MM/YYYY'`, `DefaultCurrencyId = EUR`, `PeriodStartDay = 1`). Onboarding Preferences step lets the user override all fields immediately. See ADR-0066, `docs/multi-tenancy-strategy.md`, and `docs/superpowers/specs/2026-04-28-localization-design.md`.
- [x] **WCAG 2.1 AA compliance (Phase 3)** — Full compliance required before Phase 3 launch; legally mandated by the EU Accessibility Act (Directive 2019/882, in force 28 June 2025). Operative standard: EN 301 549 v3.2.1. Implementation requirements, tooling (eslint-plugin-jsx-a11y, vitest-axe), and legal prerequisites (accessibility statement at `/accesibilidad`, feedback inbox) fully specified in `planning-phase3.md §8`. Third-party audit recommended before public launch (budget EUR 3,000–8,000).
- [x] **MVC → Web API decoupling (Phase 3)** — Approach locked 2026-04-28. Full SPA migration: Razor deleted, ASP.NET Core becomes a pure Web API, React Router handles all routing. Execution: design-first, feature-by-feature — each area is fully API-tested, then React-built, then Razor-deleted. Never a big-bang deletion. Hosting model: Option A (React build served from ASP.NET Core `wwwroot/`). See `docs/planning-phase3-spa-migration.md` and `docs/superpowers/specs/2026-04-28-spa-migration-ux-overhaul-design.md`.
- [x] **Cookie `SameSite` for the auth session cookie (Phase 3)** — `SameSite=Lax` per ADR-0063, paired with `__Host-` prefix, `HttpOnly`, `Secure`, the XSRF-TOKEN double-submit CSRF pattern, and re-authentication on sensitive operations. Strict was rejected because it breaks email-link first-navigation flows (security alerts, password reset, GDPR export ready) and would block future OAuth callbacks. See ADR-0063 and `security-model.md` § Cookie Configuration.
- [x] **EF Core global query filters (Phase 3)** — Adopted on every user-owned entity with explicit `.Where(t => t.UserId == ...)` redundancy in service code and `IgnoreQueryFilters()` reserved for the `Admin/` namespace (enforced by architecture test). Schema-per-tenant and database-per-tenant rejected for Phase 3 — operational cost dominates the security gain at beta scale. **PostgreSQL Row-Level Security: ADR-0065 originally deferred this to Phase 4; ADR-0068 (2026-05-09) overturned that and moved RLS into Phase 3 as Stage 7.5 — the deferral was based on weak rationale (overstated implementation cost, conflated user count with attack surface, contradicted ADR-0065's own "layered defence" framing).** See ADR-0065, ADR-0068, and `multi-tenancy-strategy.md` § EF Core Global Query Filters.
- [x] **Sentinel-to-real-user data migration (Phase 3)** — On first user registration, the Phase 1/2 sentinel UUID (`00000000-0000-0000-0000-000000000001`) is remapped to the new user's real `Id` across every user-owned table in a single transaction with pre-/post-checks. Preserves the developer's real personal-finance history accumulated during Phase 1/2; safe under invite-only launch. The sentinel constant is removed from the codebase in the same release. See ADR-0066 and `multi-tenancy-strategy.md` § Settings Table Migration.
- [x] **Background-job user resolution (Phase 3)** — `IUserScope.EnterAs(userId)` (foundation, returns `IDisposable`, stores the user id in `AsyncLocal<Guid?>`) plus `IUserJobRunner.ForEachUserAsync(filter, work)` (convenience layer for per-user fan-out jobs). `ICurrentUserAccessor` resolves HTTP context → background scope → throws; silent fallback to `Guid.Empty` is forbidden. Cross-tenant jobs (audit-log purge, retention sweeps) use `IgnoreQueryFilters()` explicitly per ADR-0065. `Program.cs` boot-time hooks that touch user-owned data are removed. See ADR-0067 and `multi-tenancy-strategy.md` § Background processes and non-HTTP contexts.
