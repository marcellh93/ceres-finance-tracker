# Project Ceres — Resolved Decisions Archive

Decisions that were open questions and have since been resolved. Moved here from `planning.md`
to keep the active file lean. Decisions that produced ADRs are cross-referenced.

- [x] **Authentication?** — Not needed for Phase 1/2 (local). Required in Phase 3 before hosting.
- [x] **Should accounts be linked to a currency?** — Yes. Each account has one currency. Supported at launch: EUR, USD, GBP, COP, ARS, VED. Reports filter by currency — no conversion. See models.md.
- [x] **How to handle transfers between accounts?** — Dedicated Transfer entity linking source and destination directly. No category. Excluded from all income/expense reports. Cross-currency transfers not supported. Has its own Transfer History report. See models.md.
- [x] **Number formatting and localization** — User-configurable preferences in a Settings table. Options: number format (US vs European), date format (DD/MM/YYYY, MM/DD/YYYY, YYYY-MM-DD), date separator. Phase 1: single-row app-wide settings. Phase 3: migrates to per-user preferences. See models.md.
- [x] **Starter categories** — App seeds a default set on first run (6 income, 17 expense categories). Users can add, rename, or delete any of them. Full list in planning.md Phase 1 features section.
- [x] **File attachment storage for Phase 1/2** — Local filesystem using `uploads/{transactionId}/{guid}{extension}`. Files served via controller action, not wwwroot. See models.md for StoredPath convention.
- [x] **Pagination strategy for Transaction History** — See ADR-0027. Phase 1: default view shows the most recent 50 transactions; advanced search / date range filter returns all records in the range with no cap. Phase 3: switch to offset-based pagination (`?page=1&pageSize=50`). Cursor-based deferred unless Phase 3 scale warrants it.
- [x] **Default currency when creating a new account** — Stored as `DefaultCurrencyId` in Settings (FK → Currency). Seeds to EUR on first run. Editable via Settings page. Account creation form pre-selects this currency but allows per-account override. See ADR-0015.
- [x] **Intra-day transaction ordering** — `CreatedAt datetime NOT NULL` added to both Transaction and Transfer. Set by the application on insert, never editable. Used as a tiebreaker when ordering records sharing the same Date. Default sort: `ORDER BY Date DESC, CreatedAt DESC`. See ADR-0013.
- [x] **Budget/transaction currency mismatch** — Enforced at the application level. App validates `transaction.Account.CurrencyId == budget.CurrencyId` and rejects mismatches with a validation error. No database constraint (EF Core cannot express cross-table currency match without a trigger). Integration tests must cover this aggressively. See ADR-0016.
- [x] **Category needs/wants tag for budgeting frameworks** — `LifestyleTag` varchar column added to Category (values: "Needs", "Wants", null = untagged). Seeded categories ship with suggested default tags. Users prompted at Expense category creation time. Untagged is a visible fourth bucket in the Financial Health report. See Financial Health Metrics in planning-phase2.md.
- [x] **Database backup strategy (Phase 1)** — weekly `pg_dump` via macOS `launchd` every Sunday at 7am, output to iCloud Drive (`Database backup/project_ceres_YYYY-MM-DD.sql`). Syncs off-device automatically via iCloud. Before Phase 3 launch, a managed cloud backup solution must replace this local approach.
- [x] **Opening balance cutover UX** — (1) Default starting date is today. User can change it, but the app shows an explanation of how moving the date affects their account balance and history before confirming. (2) Transactions dated before the opening balance date are blocked — not just warned. The app tells the user what they need to do to allow it (move the opening balance date first).
- [x] **Per-account balance audit trail** — Implemented as a dedicated sub-page at `/Accounts/{id}/Ledger`. Shows every entry that contributes to the account balance in chronological order with a running balance column: opening balance (IsSystem transaction), regular transactions, transfers, and liability payments. The final row's running balance must match the balance shown everywhere else in the app. This is the mechanism for validating data model correctness during Phase 1 daily use.

- [x] **Background-job user resolution (Phase 3)** — `IUserScope.EnterAs(userId)` (foundation, returns `IDisposable`, stores the user id in `AsyncLocal<Guid?>`) plus `IUserJobRunner.ForEachUserAsync(filter, work)` (convenience layer for per-user fan-out jobs). `ICurrentUserAccessor` resolves HTTP context → background scope → throws; silent fallback to `Guid.Empty` is forbidden. - [x] **Password reset flow (Phase 3, Stage 6c.1, shipped 2026-05-10)** — Two endpoints: `POST /api/auth/password-reset/request` (issues token) and `POST /api/auth/password-reset/confirm` (consumes it). Token format: 256-bit RNG, base64url-encoded, transmitted in URL fragment, persisted only as Argon2id hash in new `PasswordResetTokens` table. Lifetime 15 minutes, single-use, supersession-on-new-request via per-user `SemaphoreSlim`. **MFA gating conditional** per ADR-0069: required only when `user.TwoFactorEnabled = true`; backup codes rejected at reset (recovery path lives at `/login/totp`). On success: all `UserSession` rows revoked + `SecurityStamp` regen + lockout cleared + `EmailConfirmed` promoted + MFA-pending cookie cleared + notification email queued. Constant-time enumeration prevention via `RunDummyHash` parity on both known/unknown branches. Rate limits: per-IP 10/min via existing `AuthLoginByIp` + service-side per-email `MemoryCache` window (5/hour) returning 429 `RATE_LIMITED` with `Retry-After`. New `IEmailService` abstraction with dev-only `LogOnlyEmailService`; production deliberately throws at startup until Stage 8 wires the real provider. New `INVALID_RESET_TOKEN` canonical error code added to `api-contract.md`. New `PasswordResetUnknownEmail` value added to `FailedLoginReason` for cross-tenant observability. 46-test ship-gate green across happy path, no-MFA confirm, MFA confirm, concurrency, rate-limits, session-revocation, and architecture rules. See `security-model.md → Password Reset`, `docs/superpowers/specs/2026-05-10-password-reset-design.md`, and `docs/superpowers/plans/2026-05-10-stage-6c-1-password-reset-plan.md`.
- [x] **Reauth middleware for sensitive operations (Phase 3, Stage 6c.2, shipped 2026-05-10)** — `LastReauthAt` claim (Unix seconds) stamped on the auth cookie at login (no-MFA + MFA + backup-code paths) and refreshed by a successful `POST /api/auth/reauth` step-up. `[RequireRecentAuth]` attribute backed by `RecentAuthRequirement` policy + custom `IAuthorizationMiddlewareResultHandler` emitting `401 REAUTH_REQUIRED` when the claim is missing, malformed, future, or older than 5 minutes. Reauth endpoint validates `password` (no MFA) or `totpCode` (MFA) based on `user.TwoFactorEnabled`. Backup codes are NOT accepted at reauth (recovery path is `/login/totp`). Wrong password counts toward lockout via `AccessFailedAsync`; wrong TOTP does not (uses `VerifyTwoFactorTokenAsync` directly). Per-user rate limit 10/min via `AuthReauthByUser` (uses explicit `httpContext.AuthenticateAsync(IdentityConstants.ApplicationScheme)` to resolve the partition key — the rate-limit middleware runs before `UseAuthentication`). `RefreshSignInAsync` preserves the existing `sid` claim across the cookie refresh so `SessionRevocationValidator` continues to identify the session. Three existing MFA endpoints (`/api/auth/mfa/enroll`, `/enroll/verify`, `/backup-codes/regenerate`) retroactively gated; the in-body TOTP-code stopgap from Stage 6b.3 Gap 4 was removed and the `RegenerateBackupCodesRequest` DTO deleted. New canonical error codes: `INVALID_REAUTH`, `REAUTH_REQUIRED`. 32-test ship-gate. **Follow-up flagged:** `AuthMfaByUser` (Stage 6b.3) shares the rate-limit-partitioning bug fixed here for `AuthReauthByUser` — its existing test asserts only "any 429 fires" and so doesn't catch it; same `AuthenticateAsync(TwoFactorUserIdScheme)` fix applies and is tracked separately. See `security-model.md → Login → Reauthentication`, `docs/superpowers/specs/2026-05-10-reauth-middleware-design.md`, and `docs/superpowers/plans/2026-05-10-stage-6c-2-reauth-middleware-plan.md`.
- [x] **Email-address-change flow (Phase 3, Stage 6.12, shipped 2026-05-10)** — Three endpoints: `POST /api/auth/email-change/request|confirm|revoke`. Single `EmailChangeTokens` table with `Purpose` discriminator (`VerifyNew=1` 30-min, `RevokeOld=2` 7-day) — chosen over two separate tables for index parity with `PasswordResetTokens` and one-statement sibling consume. Custom 256-bit base64url tokens hashed with the project Argon2id hasher (mirrors Stage 6c.1; Identity's `GenerateChangeEmailTokenAsync`/`ChangeEmailAsync` are not used because they have one global `TokenLifespan`, no built-in single-use, and no two-token-one-event semantics). **Three policy decisions resolved during this stage:** (1) `/confirm` and `/revoke` are anonymous — the email-link token IS the auth; only `/request` is `[RequireRecentAuth]`-gated. AllowAnonymous lives on the actions, not the controller class. (2) `/confirm` revokes all sessions and regenerates `SecurityStamp`; `/revoke` does NEITHER — revoke is a cancel-pending-change, not a security event for the legitimate user. (3) A successful `/api/auth/password-reset/confirm` atomically cancels any pending email-change for the same user and notifies the old address — closes the window where an attacker-initiated change with a still-live verify token could survive a victim's password-reset. On `/confirm`: `SetEmailAsync` + `SetUserNameAsync` (registration sets `UserName == Email`; only updating `Email` would leave `FindByNameAsync(oldEmail)` resolving the user), `EmailConfirmed = true`, sibling `RevokeOld` row consumed atomically, all `UserSession` rows revoked, notifications to BOTH new and old addresses (per security-model.md "Notify the old address on successful completion of the change"). **Explicit divergence from password-reset:** `/confirm` does NOT clear lockout — email proof ≠ password recovery. Per-user `SemaphoreSlim` for concurrency; per-IP `AuthLoginByIp` (10/min) on `/confirm` and `/revoke`; per-new-email service-side `MemoryCache` window (5/hour) on `/request`. New canonical error codes: `INVALID_EMAIL_CHANGE_TOKEN` (401), `EMAIL_ALREADY_IN_USE` (422), `EMAIL_UNCHANGED` (422). 37-test ship-gate. Small architectural cleanup applied along the way: dropped redundant explicit `[Authorize]` on `RequestChange` because `[RequireRecentAuth]` already inherits `AuthorizeAttribute`; the duplicate would have tripped the singular-attribute lookup in `Every_controller_action_declares_authorization_intent`. See `security-model.md → Email Address Change` and `docs/superpowers/specs/2026-05-10-stage-6-12-email-change-design.md`.
- [x] **`AuthMfaByUser` rate-limit partition bug (Phase 3, Stage 6c.2 follow-up, shipped 2026-05-11)** — Same partition-collapse bug fixed in 6c.2 for `AuthReauthByUser`, applied to the MFA endpoints. The wall is now enforced on **24 user-owned tables** at the database layer. **Three Postgres roles** (`scripts/setup-postgres-roles.sql`): `ceres_app` (runtime, NOBYPASSRLS), `ceres_admin` (admin services + `IUserJobRunner`, BYPASSRLS), `ceres_migrator` (DDL + BYPASSRLS). Migration `AddRowLevelSecurityPolicies` runs three phases: (A) attachment-table `UserId` schema additions to `TransactionAttachments` + `TransferAttachments` with backfill from parent movement; (B) `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY` + `user_isolation` policy on each of the 24 tables; (C) defensive check that `ceres_admin` retains `BYPASSRLS`. Policy SQL uses `NULLIF(current_setting('app.current_user_ref', true), '')::uuid` to handle Postgres's documented quirk that `DISCARD ALL` resets custom-namespace GUCs to empty string (not NULL) — without `NULLIF` every pooled-connection reuse would raise `22P02 invalid input syntax for type uuid: ""`. **Mechanism correction during implementation:** the spec's per-command `IDbCommandInterceptor` issuing `SET LOCAL` is unsafe for this codebase — EF Core 7+ bulk operations (`ExecuteDeleteAsync`, `ExecuteUpdateAsync`) do not open an EF transaction and `SET LOCAL` outside a transaction is a no-op, so production paths using bulk ops (`LockoutUnlockService`, `EmailChangeService`, `MfaBackupCodeService`, `TotpReplayGuard`, `UserBlockedIpMiddleware`) would have silently bypassed the GUC. Replaced with `DbConnectionInterceptor.ConnectionOpenedAsync` issuing `SELECT set_config('app.current_user_ref', '<uuid>', false)` (session scope) once per pooled-connection acquisition; on `Guid.Empty` the interceptor issues `RESET` as belt-and-braces in case `No Reset On Close=true` is ever set (required for pgBouncer transaction mode). `BackgroundJobScope.RunAsync(userId, jobName, work)` is the single doorway for background-job entry into a user-scoped context — refuses `Guid.Empty` with `LogError` + `InvalidOperationException` before invoking work; an architecture test (`ArchitectureTests.EnterAs_only_called_inside_BackgroundJobScope`) pins that `.EnterAs(` is only called from `BackgroundJobScope.cs`. `UserJobRunner` updated to route through the wrapper. `PrivilegeLeakStartupCheck` at `Program.cs` boot refuses to start if `ApplicationConnection` is wired to a DDL-capable role (CREATE TABLE → expects 42501; if it succeeds, exit).
