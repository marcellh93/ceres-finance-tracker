# ADR-0058 — Movement Base Class: Table Per Concrete Type (TPC)

**Status:** Accepted
**Phase:** 2 (Stage 2.5)

---

## Context

`Transaction`, `Transfer`, and `LiabilityPayment` share six columns: `Id`, `Date`, `Amount`, `Description`, `IsCleared`, and `CreatedAt`. Before Stage 2.5 these were duplicated independently across three entities with no shared model layer. The goal of Stage 2.5 is to:

1. Formalise this shared shape at the C# model layer via an abstract `Movement` base class.
2. Enable a unified `/Movements` ledger view that queries all three types together in a single sorted result.
3. Avoid any schema migration — the three existing DB tables must remain exactly as-is.

Three EF Core inheritance strategies were evaluated.

---

## Decision

Use **Table Per Concrete type (TPC)**.

EF Core resolves `db.Set<Movement>()` as a SQL `UNION ALL` across the three concrete tables. Each table retains its existing schema unchanged. No base table is introduced. No migration is required beyond a configuration-only change in `AppDbContext.OnModelCreating`.

---

## Alternatives rejected

**TPH — Table Per Hierarchy**
Would merge `Transactions`, `Transfers`, and `LiabilityPayments` into a single table with a discriminator column. Rejected: destroys the existing schema, requires a large destructive migration, and produces a wide sparse table.

**TPT — Table Per Type**
Adds a shared `Movements` base table that EF joins against on every query. Rejected: introduces an unnecessary join on every movement query, adds a migration, and provides no benefit over TPC for this schema shape.

---

## Consequences

- `Transaction`, `Transfer`, and `LiabilityPayment` inherit from `Movement`; the six shared properties are removed from each concrete class and promoted to the base.
- `AppDbContext` gains `DbSet<Movement>` and configures `UseTpcMappingStrategy()` on `Movement`.
- The migration generated by `dotnet ef migrations add TpcMovementHierarchy` must have an empty `Up()` and `Down()`. If any schema-altering operations appear, stop and investigate before applying.
- All existing service interfaces and implementations are unchanged — the inheritance refactor is invisible to callers.
- All existing tests must pass without modification after the refactor.
- The `/Movements` unified ledger view is the primary consumer of `db.Set<Movement>()`. `/Transactions` and `/Transfers` remain fully functional as secondary views.
- `returnUrl` routing is added to `TransactionsController` and `TransfersController` Edit and Delete actions so that navigating from `/Movements` returns the user to `/Movements` after save or delete.
- The `ClearedBadge` React component (Stage 2.5.3) calls `PATCH /api/movements/{id}/cleared` for inline async toggling on list views. A separate `IsClearedSwitch` React component handles the `IsCleared` field on Edit forms — it writes to a hidden form field submitted with the standard form POST, with no API call.
